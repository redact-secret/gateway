# ADR 0018: SSE relay, stream termination contract, and stream bounds

Status: Accepted. Implementation status: implemented for `stream: true` on the approved Chat Completions text subset (#21); SDK qualification against a Gateway wired to a fake provider is done in #22 ([ADR 0020](0020-sdk-qualification-test-build.md)); it corrected decision 9 below. Numeric values are **provisional pending quiet-host measurement** (ADR 0008). Date: 2026-10-02. Implements the #3 design contract for issue #21 on top of [ADR 0002](0002-request-states-and-forwarding-authority.md), [ADR 0003](0003-resource-admission-and-lifetime.md), [ADR 0004](0004-cancellation-and-synchronous-core-work.md), [ADR 0008](0008-performance-measurement-gate.md), [ADR 0013](0013-fixed-https-destinations-and-outbound-authority.md), [ADR 0016](0016-header-allowlists-and-request-local-credentials.md), and [ADR 0017](0017-json-forwarding-deadlines-and-cancellation.md), and replaces ADR 0017 decision 8 (`stream: true` interim `501`).

## Context

#20 sends the sealed request once and relays a complete, bounded JSON answer, so every failure still has a real status code. A streamed answer cannot be buffered (that would accumulate the whole response and delay every event), and once its headers are sent the status can no longer change. The Gateway needs one documented way to bound, cancel, and end a stream that never hides an interruption.

## Decision

1. **Same road, no bypass.** `stream: true` takes exactly the #18/#19/#20 path: the whole request is received, admitted, parsed, inspected, and sealed before any upstream byte. Every rejection (admission, parse, matrix, inspection, a missing credential, overload of any class) sends zero upstream bytes. The inspection permit and the request's memory reservation are released as before: inspection when its job ends, memory when the response headers arrive; neither is held for the stream's life. A `stream: true` request from an HTTP/1.0 caller is rejected locally (`422 unsupported_input`): a stream to such a caller would be delimited by connection close, so a cut stream could not be told from a finished one.
2. **A sibling entry point.** `Upstream::forward_stream(SanitizedRequest, VettedHeaders, UpstreamPermit, StreamPermit)` takes the same sealed request and request-local credential as `forward`. There is still no overload for bytes, validated requests, or JSON, and no raw-body fallback (compile-fail test `tests/ui/fail_forward_stream_bytes.rs`). The route acquires, in ADR 0003 order, the upstream permit and then the stream permit with `try` (a full class is an immediate `503 overload`, nothing sent), after inspection has finished.
3. **What is a stream.** Only a `2xx` answer with exactly one `Content-Type: text/event-stream` and an explicit end of message (chunked or counted) is relayed incrementally. Anything else (a provider `4xx`/`5xx` such as `401` or `429`, a JSON answer to a streaming request) is read under the ordinary #20 bounds and deadlines and relayed as a normal response; the stream permit is released. A close-delimited event stream is refused as `502 upstream_invalid_response` before any byte is relayed, because an interrupted one cannot be told from a finished one and the Gateway must not make a truncated stream look normal.
4. **Bytes, not events.** The relay forwards each provider body chunk unchanged. It does not parse event boundaries or UTF-8, does not assume a transport chunk is an event, merges nothing, splits nothing, redacts nothing, and adds nothing. Events split across chunks, several events in one chunk, and multibyte characters split across chunks arrive byte-exact. Provider response content is unredacted and never enters logs, telemetry, errors, or `Debug` output. Headers use the #24 response allowlist.
5. **No tasks, no queues; backpressure by construction.** The response body (`transport::stream::StreamBody`) is polled by the HTTP server that owns the response and polls the provider body inline. The server asks for a chunk only when it can accept one, so a slow consumer backpressures the provider through TCP, and the relay holds at most one provider chunk. The Gateway spawns nothing per stream: task count is the HTTP server's connection tasks and the client's connection tasks, bounded by the stream and upstream permits (test: tasks grow by at most two per open stream, the fake provider's plus the client's, and return to baseline).
6. **Independent capacity held for the real lifetime.** The body owns the `UpstreamPermit` and the `StreamPermit` from the response headers until the stream ends, fails, or the body is dropped. It closes the provider connection first and returns the permits second, so capacity returns only after the exchange is closed. Stream capacity is independent of every other class: a long-lived or slow stream occupies an upstream slot and a stream slot and nothing else, so it cannot exhaust inspection, receipt, or memory capacity (test: with one inspection slot, a second stream completes inspection while the first stays open, and the whole memory budget is free). Aggregate relay memory is bounded by `resources.capacity.stream * resources.limits.stream_buffer_bytes`, which configuration validation caps at 4 GiB; the HTTP server's own write buffer is bounded by the library, outside this configuration.
7. **Deadlines and bounds (provisional, finite, static config under `resources.limits`).**
   * `stream_idle_ms` 120,000 (ceiling 3,600,000; not above the lifetime): longest wait for the next provider chunk, counted only while the Gateway waits on the provider, never while the consumer is slow. A stalled provider ends the stream.
   * `stream_lifetime_ms` 900,000 (ceiling 3,600,000): longest total life from the send. Infinite streams are a non-goal.
   * `stream_write_stall_ms` 30,000 (ceiling 600,000): longest a pending response write may make no progress. Enforced for every accepted connection by an IO wrapper (`write_stall`), with no task: the timer runs inside the pending write and restarts on progress. A consumer that stops reading is cut after this deadline; the server then drops the response, which closes the provider connection and returns the permits. A consumer that keeps making slow progress is bounded by the lifetime deadline instead. This also bounds a stalled reader of an ordinary buffered response.
   * `stream_buffer_bytes` 1,048,576 (ceiling 16,777,216): the most provider bytes the relay holds at once. One provider chunk above it ends the stream. The HTTP client library's read buffer (about 400 KiB at most) is below the default, so a legitimate stream does not reach it; a configured value below that can end a stream with a large burst.
   The response-header deadline (`upstream_header_ms`) still bounds the wait for headers; `upstream_total_ms` applies only to buffered answers.
8. **Termination contract.** Before the response headers are committed, every failure is the normal #20 Gateway error (`502`/`504` with `upstream_*` codes, `503 overload`, `501`, local rejections). **After the headers are committed no status can change.** Every failure then ends the stream abruptly: the body reports an error to the HTTP server, which closes the connection without the terminating chunk (the server speaks HTTP/1.1 only). The caller sees a truncated, errored stream, never a normal end. The Gateway writes no completion event, no `data: [DONE]`, no error event, and no text into the stream. A normal end (with the terminating chunk) is produced only when the provider itself ended the response cleanly. The causes, each a closed counter and none visible to the caller beyond the truncation: provider connection error or malformed or truncated response, idle deadline, lifetime deadline, a chunk over the buffer bound, shutdown cancellation, and (a body dropped before the end) caller disconnect or write stall.
9. **SDK behavior (observed in #22 with the pinned SDKs; corrected from the earlier unverified text).** After the response headers, a broken stream is ended abruptly with no terminating chunk and no completion event. The **Python** SDK (`openai` 3.24.0, httpx) raises `APIConnectionError` and delivers only the events the provider really sent. The **Node.js** SDK (`openai` 7.27.0, Node's built-in fetch, undici) depends on the Node.js version: on Node.js 24 it raises, and on Node.js 22.16.0 (undici 6.21.2) it did **not**, because every gateway response carries `Connection: close` (ADR 0019) and that undici treats the close of a chunked body as a clean end (a control run shows it does raise for the same truncation on a keep-alive response). Neither SDK retried a stream cut after the headers (one request); the earlier text here said they may. Node applications must therefore require the provider's own completion indicator (`finish_reason`) before trusting a stream, on every version. The Gateway adds no retry, no replay, no resume, and no fabricated completion. Bytes already transmitted to the caller cannot be retracted. A change to the connection signalling of truncated streams (for example an abortive close) is a possible follow-up and is not part of this ADR.
10. **Cancellation and shutdown.** A caller that disconnects makes the server drop the response, which drops the body: the provider connection is closed and both permits return. On shutdown the server stops accepting and drains for at most `shutdown_drain_ms`; then `ChatRoute::cancel_in_flight` ends the request futures and also every open stream (each ends abruptly per 8), and `serve` returns within the existing one-second grace. There is no replay. Bytes already written to the provider cannot be retracted, so a cancelled request may still have been received and acted on.
11. **Telemetry (ADR 0008).** Closed vocabulary, counters and timings only: stage timings for stream first byte, stream total, stream upstream wait (time waiting on the provider), and stream downstream wait (time between handing a chunk to the server and the server asking for the next, that is consumer and socket backpressure); relay overhead is total minus both. Counters: streams started, streams ended by cause, provider bytes relayed, and the bytes the relay holds now and at peak. No stream content, key, header value, or route is a label.

## Consequences

- A truncated stream is visible to the caller only as a closed connection. That is deliberate: any in-band signal would be a fabricated provider event.
- Latency of the first byte is the provider's. A non-SSE answer to a streaming request is buffered and relayed like #20.
- A fresh provider connection per request (ADR 0017) applies to streams too.
- The write-stall deadline cuts slow-loris style readers of any response on any connection; legitimate local consumers read fast. It does not bound read-side stalls; the request head is bounded since #25 ([ADR 0019](0019-request-head-guard-and-one-request-per-connection.md)) and the body by `body_deadline_ms` (#18), while the connection count remains unbounded (resource-limits, #10).
- Peak relay buffer is measured as the single provider chunk in flight to the server. The server's own buffering and kernel socket buffers are not counted; tests therefore also check that a provider writing as fast as it can stops making progress while the consumer is stalled.
- All numbers are provisional.

## Test evidence

End-to-end tests in `src/transport/tests/stream_tests.rs` run the whole route against the loopback fake provider (reachable only through `#[cfg(test)]` items, per ADR 0013): fragmented SSE including Korean and emoji text relayed byte-exact at fragment sizes 1 to 64; several events in one chunk and events split across chunks; no completion event added to a provider stream that has none; a normal end has the terminating chunk and an idle-cut stream on the wire does not; termination for provider cut, malformed framing mid-stream, idle, lifetime, and over-buffer chunks, all after a committed `200`, each with partial provider bytes preserved, no fabricated completion, one upstream request, the provider connection closed, and permits back at baseline; pre-header failures as ordinary Gateway errors; provider `4xx`/`5xx` and JSON answers relayed as responses; zero upstream bytes for every rejection path including each class at capacity and HTTP/1.0; a slow consumer backpressuring an unbounded provider (its writes plateau), peak relay buffer within the bound, the stall deadline cutting the connection and cancelling upstream, and upstream wait distinguished from consumer wait; downstream disconnect cancelling the provider stream; shutdown cancelling open streams and the drain deadline bounding `serve`; inspection, receipt, and memory capacity independent of stream occupancy; stream capacity bounding streams, upstream occupancy, and tasks; a cancelled inspection wait never starting a stream; leak scans over errors, headers, and `Debug` output. `src/write_stall.rs` has unit tests for the stall timer. Compile-fail and pass tests cover the `forward_stream` signature.

Amendment (#87): `POST /v1/responses` uses this relay unchanged: both endpoints are the same `EndpointRoute` over the same transport, permits, limits and write-stall listener, so every bound, termination rule and cleanup rule in this ADR holds for Responses streams and Responses JSON answers.
