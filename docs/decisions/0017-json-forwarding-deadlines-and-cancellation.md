# ADR 0017: Ordinary JSON forwarding, deadlines, response bounds, and cancellation

Status: Accepted. Implementation status: implemented for ordinary (non-streaming) JSON requests and responses (#20); SSE relay is planned (#21); SDK qualification is planned (#22). Numeric values are **provisional pending quiet-host measurement** (ADR 0008). Date: 2026-10-02. Implements the #3 design contract for issue #20 on top of [ADR 0002](0002-request-states-and-forwarding-authority.md), [ADR 0003](0003-resource-admission-and-lifetime.md), [ADR 0004](0004-cancellation-and-synchronous-core-work.md), [ADR 0008](0008-performance-measurement-gate.md), [ADR 0009](0009-credential-and-upstream-trust-model.md), [ADR 0013](0013-fixed-https-destinations-and-outbound-authority.md), and [ADR 0016](0016-header-allowlists-and-request-local-credentials.md).

## Context

Admission (#18), inspection and sealing (#19), fixed destinations (#23), and header and credential rules (#24) exist. Nothing sends a body yet. The route must connect the sealed request to the central transport without opening a second path to the network, bound every wait and buffer, relay the provider's answer, and give cancellation and shutdown a defined, testable end.

## Decision

1. **One forwarding path.** `ChatRoute::process` hands the `SanitizedRequest`, the request-local `VettedHeaders` (`Admitted::take_headers`), and an `UpstreamPermit` to `Upstream::forward`. Protocol and route code build no request and hold no client. There is no overload for bytes, validated requests, or JSON, and no raw-body fallback. The compile-fail API-boundary tests now include the headers and permit parameters.
2. **Independent upstream capacity.** The `UpstreamPermit` is acquired with `try_upstream` after inspection has finished and released its permit (ADR 0003 order: receipt, memory, inspection, upstream, stream). A full upstream class is an immediate `503 overload` with `Retry-After: 1`; nothing was sent. The permit travels inside the buffered response and is released only when the response body has been written or abandoned, so buffered provider bytes are always attributable to a held upstream slot (`upstream * max_response_body_bytes` bounds them). The sealed request, and with it the memory reservation, lives until the exchange ends.
3. **One send, no retry, no replay.** Exactly one `send` per request. The client has idle pooling off (`pool_max_idle_per_host(0)`), so the HTTP library can never re-send a request on a stale reused connection. Cost: a TCP and TLS handshake per request; this is a provisional correctness-over-latency choice to revisit with measurement (ADR 0008) and a reviewed no-replay argument for pooling. Redirects stay off (#23). A connect-phase failure is reported as such; any failure after the send began terminates with a safe error and never produces a second attempt or a fallback.
4. **Deadlines (provisional, finite, static config under `resources.limits`).** `upstream_connect_ms` 5,000 (ceiling 60,000), applied on the client; `upstream_header_ms` 120,000 and `upstream_total_ms` 300,000 (ceiling 3,600,000 each; header must not exceed total), applied per request from just before the send. A non-streamed completion is answered only when generation ends, so the header deadline is long; the numbers are ceilings chosen to be safe, not tuned values. The deadline is checked immediately before the send is initiated.
5. **Response bounds (provisional).** `max_response_header_bytes` 32,768 (ceiling 262,144) counts names, values, and framing after parsing; the HTTP parser itself caps the field count at 64 and its own buffer is the hard parse-time ceiling, so the configured value cannot reduce what the parser reads, only what is accepted. `max_response_body_bytes` 4,194,304 (ceiling 67,108,864): a declared `Content-Length` over the cap is refused before reading, and an undeclared or chunked body is counted and refused at the cap, so nothing is accumulated beyond it. The body is buffered and relayed only when complete, so every bound or failure is reported with a real status before any response byte is committed: `502 upstream_response_too_large`.
6. **Relay.** The provider's status is relayed unchanged, including `4xx` and `5xx`, which are provider responses and not Gateway errors. Headers go through the #24 allowlist (`relay_response_headers`); framing is regenerated by the server from the exact buffered length. A response with a `Content-Encoding` other than `identity` is not relayable and is `502 upstream_invalid_response`. The body is relayed **unredacted**; provider response and error bodies can contain sensitive data, never enter Gateway logs, telemetry, or errors, and the response type's `Debug` prints status and length only.
7. **Safe transport errors** (`upstream_timeout` 504, `upstream_unavailable` 502, `upstream_tls_failure` 502, `upstream_invalid_response` 502, `upstream_response_too_large` 502) with the SDK-retry analysis live in the [errors-and-telemetry contract](../contracts/errors-and-telemetry.md). Classification uses the client error's structure; for TLS it inspects the lowercase source-chain text only to choose a category and never stores or returns it.
8. **`stream: true` interim behavior.** A streaming request is admitted (the same receipt, memory, and parse costs, so it is bounded like any request) and then rejected locally with `501 not_implemented` **before** inspection and before any upstream permit or byte. It is never forwarded as a JSON relay, because buffering an SSE stream would violate the no-accumulation rule and hand the caller a malformed result. A deployment with no `deployment.upstream` also answers `501 not_implemented` after inspection, without touching the network. #21 replaces the first with SSE relay (`StreamPermit`, idle and lifetime deadlines).
9. **Cancellation.** The request handler future owns everything (waits, the inspection await, permits, buffers, the exchange); nothing is spawned. When the caller disconnects, hyper drops the future, which cancels the exchange, closes the provider connection, and releases the memory reservation and permits through RAII. A dropped inspection await cancels only the wait: the worker job owns its permit and memory until the core call really ends and its result is discarded (ADR 0004), so a cancelled waiter can never reach `forward`. **Bytes already written to the provider cannot be retracted**, so a cancelled or timed-out request may still have been received and acted on. No exactly-once or at-most-once claim is made.
10. **Shutdown.** On a termination signal the server stops accepting, readiness turns false, and in-flight requests drain for at most `shutdown_drain_ms` (provisional 10,000; `0` to 600,000). Then `ChatRoute::cancel_in_flight` ends every request future (each answers `503 not_ready` if its caller is still connected) and `serve` returns after at most a one-second grace for connections to close. Connection tasks are owned by the HTTP server and the runtime; none is detached by this code.
11. **Telemetry (ADR 0008, minimum).** `telemetry::Metrics` keeps count, total, and maximum microseconds for admission wait, parse, inspection, serialization, upstream first response, and upstream total, plus an upstream-attempt counter. The label set is a closed enum; there is no exporter and no payload, route, or credential dimension.

## Consequences

- JSON latency includes the full provider generation time before the first byte reaches the caller (the response is buffered). That is the price of reporting every failure with a real status; SSE is the incremental path (#21).
- A fresh connection per request is slower than pooling. Revisit with a measurement and an explicit no-replay review.
- The response header cap is enforced after parsing, so a hostile provider can make the parser read up to its buffer limit; only reviewed providers are reachable (ADR 0013), so this is accepted.
- `shutdown_drain_ms` and the other deadlines are provisional and unmeasured. They are finite and validated, nothing more.
- Provider-side effects of a cancelled or timed-out request cannot be undone.

## Test evidence

End-to-end tests in `src/transport/tests/forward_tests.rs` run the whole route against the loopback fake provider (reachable only through `#[cfg(test)]` items, per ADR 0013): exact sanitized body and vetted headers; planted secrets absent upstream and placeholder present; zero upstream bytes for every pre-forward failure including overload at each class and a cancelled waiter; one connection and one request for every post-forward failure; provider `4xx`/`5xx` relayed unchanged; downstream disconnect, shutdown cancellation, and the drain deadline returning every permit; concurrent distinct synthetic keys not crossing; no client construction or configuration parse per request; stage timings recorded; leak scans over errors and `Debug` output.

## Open item: SDK qualification (#22) without a production seam

The #20 acceptance item "JSON response/status handling works with pinned Node/Python clients" needs a Gateway whose upstream is a local fake, and the destination policy (ADR 0013, `tests/destination_policy.rs`) forbids any feature, flag, environment variable, or configuration path to one in a release binary. #20 does not work around that. Proposal for #22: an explicitly separate, non-release test build, outside the shipped artifacts and outside the release workflow, produced only by a dedicated test crate or workflow (never by `--features` or `--cfg` on the shipped targets), whose provenance is distinct and which is never published. Because that necessarily relaxes the scans in `tests/destination_policy.rs`, the maintainer updates those policy tests deliberately in that change. Until then the item stays unchecked.
