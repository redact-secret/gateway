# ADR 0016: Header allowlists and request-local provider credentials

Status: Accepted. Implementation status: implemented (inbound vetting, credential type, outbound wire headers, response-header allowlist); sending and relaying of ordinary JSON responses are implemented in #20 ([ADR 0017](0017-json-forwarding-deadlines-and-cancellation.md)); SSE relay is implemented in #21 ([ADR 0018](0018-sse-relay-termination-and-stream-bounds.md)). Date: 2026-10-02. Implements the #3 design contract for issue #24 on top of [ADR 0009](0009-credential-and-upstream-trust-model.md), [ADR 0013](0013-fixed-https-destinations-and-outbound-authority.md), and [ADR 0014](0014-chat-completions-admission.md).

## Context

Alpha uses caller-supplied provider credentials. Something must decide which caller headers can matter, keep the credential out of shared state, logs, and model text, and build outbound headers and framing that a caller cannot steer. Beta 1 will add a separate local caller token that must never be confused with the provider credential.

## Decision

1. **Build, do not copy.** `vet_inbound` extracts only the provider credential and two reviewed metadata values from the caller's headers; `wire_headers` constructs the entire outbound header set from those plus fixed values and the sealed body length. Nothing else can reach the wire, so the hop-by-hop list, `Forwarded`/`X-Forwarded-*`, cookies, SDK telemetry, and any future local-authority header are excluded by construction rather than by a denylist that could be incomplete. `Connection` is still parsed so a nominated header is treated as removed (including `Authorization`), and ambiguous nominations are rejected.
2. **Strip versus reject.** Ignore (strip) headers that are merely irrelevant or unreviewed; reject forms that make the request ambiguous or unsafe to interpret: duplicate or malformed credential, malformed or repeated organization/project, malformed `Connection`, `Upgrade`, non-`100-continue` `Expect`, oversized headers. Exact table in [the contract](../contracts/headers-and-credentials.md).
3. **Organization/project** are forwarded when syntactically valid: they select billing and project context at the provider and are caller-supplied provider authority like the key. Not forwarded: `OpenAI-Beta` and all others (not needed for Chat Completions text).
4. **Fixed gateway values** for `Content-Type`, `Accept`, `Accept-Encoding: identity`, and `User-Agent`. The gateway relays provider bytes without decoding, so it must not negotiate a content coding.
5. **Credential type.** `ProviderCredential` has a redacted `Debug` and no `Clone`/`Display`/serialization; `VettedHeaders` is consumed by `Upstream::outbound`. Missing credential is a distinct `401 missing_credential` rather than reusing an input category, so a caller can tell it from a body problem and so it can never be read as a local-auth result. Duplicate or ambiguous credential is `400 malformed_input`.
6. **Local authority is separate.** Reserved namespace `X-Gateway-Local-*`; its own type and module in #12; `Authorization` stays the provider credential. The reservation and the leak tests came with #24; the token itself (`X-Gateway-Local-Token`, `transport::local_auth`) was added by #63 (ADR 0030) and is consumed locally, never forwarded.
7. **Response headers** are allowlisted for relay, with `Content-Encoding` other than `identity` treated as non-relayable. Framing is regenerated by the gateway's server.
8. **Framing.** Rely on the HTTP layer where it rejects; pin the observed outcomes in tests. The one gap this ADR recorded, `Content-Length` with `Transfer-Encoding` (the layer resolves it before the handler), was **closed in #25** by a connection-level head guard that fails the connection before the parser sees such a head ([ADR 0019](0019-request-head-guard-and-one-request-per-connection.md)); the operator requirement for fronting proxies remains. Provider-bound framing is unaffected because it is regenerated.

## Owner

`transport` (`headers`, `credential`, `Upstream::outbound`). `chat_route` calls `vet_inbound` and carries the result on `Admitted`. The maintainer approves any change to the allowlists.

## Invariants

1. No outbound header comes from a caller except the vetted credential and organization/project.
2. The provider credential is request-local, never in shared state, models, logs, errors, or `Debug` output.
3. Outbound `Content-Length` equals the sealed body length; `Host` comes from the reviewed destination.
4. Local authority never substitutes for, or travels with, the provider credential.

## Failure behavior

Rejections are local, before any capacity reservation or upstream contact, with the safe codes in the contract. Transmission failure after any byte is sent ends without replay (no retries).

## Implementation handoff

- #20: take the vetted headers with `Admitted::take_headers()` (before `into_parts`), call `Upstream::outbound(headers, &sanitized)`, send, and keep the `SanitizedRequest` alive until the send completes. Apply `relay_response_headers` to the provider response.
- #21 (implemented, [ADR 0018](0018-sse-relay-termination-and-stream-bounds.md)): streaming relay; response headers go through the same allowlist, once, when they arrive.
- #12: local caller token under `X-Gateway-Local-*`.

## Deferred measured choices

Header byte limits (16 KiB total, 8 KiB value) and the 512-byte token cap were provisional and unmeasured (the header limits are now measured and confirmed, [ADR 0023](0023-header-size-measurement-and-size-classes.md)); they only need to exceed legitimate SDK headers. The single body copy in `outbound` is not separately reserved; #20 should decide whether it is accounted.
